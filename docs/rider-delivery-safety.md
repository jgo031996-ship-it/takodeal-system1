# Rider approval and delivery safety

The Rider app must validate its phone/PIN account against a fresh active or approved rider record. Pending, rejected, banned, unknown, unavailable and ambiguous records cannot open the operational app. ID-only session restoration is removed; riders sign in with their phone and PIN after reloading. Approval remains an explicit Manager decision.

`rider-delivery-safety.js` is identical in the Rider and Owner apps. It uses current session capture/assert hooks from the Rider account controller before and after every asynchronous read. Transactions read current rider approval and order ownership, then save related changes together. Existing order states remain compatible: claiming a ready delivery or accepting its exact targeted ping sets `out_for_delivery`; completion sets `completed`. Optional pickup records metadata without introducing another status.

For cash delivery, wallet debit remains the existing `totalAmount`, including any retained delivery fee. This change does not redefine Rider earnings, calculate a different fee, create remittances, or adjust past wallets. For prepaid delivery, the wallet is not debited. The actual `paymentMode` (Customer) or `paymentMethod` (POS) is checked; contradictory fields fail. Prepaid requires one exact same-branch receipt, read again inside the transaction, with `paymentVerified === true`, a noncash payment method, and no void/unpaid status. Mobile receipt `paymentStatus: paid` alone records POS encoding and is insufficient for HQ verification.

Claim and wallet debit are one transaction. Top-up approval and wallet credit are one transaction. Existing order/request documents hold stable operation markers, including actor UID, intent, amount and timestamps, so contention and uncertain acknowledgement retries do not repeat a financial movement. A different attempt cannot reopen a reviewed top-up. Fresh approval/scope and actor identity are still required on retries. Orders, receipts, inventory movements, existing remittances and historical wallet entries are not recalculated.

Completion requires current ownership and ongoing status; delivery proof must have been uploaded before the transaction. A saved proof URL is reused on an uncertain acknowledgement retry. Ping rejection retains all previous `declinedBy` entries and checks the current ping target before clearing it. A stale decline cannot clear a newer assignment. A pending top-up request uses a stable ID and exact proof/reference intent; retry preserves any later approved/rejected review. Availability is changed only after a successful fresh-approved-rider transaction.

`installRiderManagementSafety` overrides the legacy approval and top-up mutation handlers after Owner main initialization. It requires the currently unlocked verified Google identity, fresh canonical saved HQ `riders` permission, and explicit saved branch scope. The main verified Owner can review the legacy global fleet. Other HQ accounts need `All` scope for a rider without a narrower assignment; explicit rider assignments must fit the Manager's saved branches. No role label grants extra permission. Approval modal state is rechecked inside the transaction; each decision records its previous status and reviewer.

## Existing trust boundary

These transactions are client correctness protection, not a completed Rider authorization migration. Current published legacy rules use `isHQUser() = isSignedIn()` for `riders` and `rider_topups`; the Rider app signs in anonymously. Incoming order status/assignment/proof fields also have broad legacy update access. A custom client can bypass client checks. These changes do not tighten, publish or claim to fix those Rules. Server-bound Rider identity, approval authority, private registration documents and a review of existing public delivery/customer data require a separate coordinated policy migration. Existing Staff private-document rules and broker are not repurposed for Rider files.

The legacy ping listener has no corresponding `looking_for_rider` producer in the released Customer/POS source. It is retained safely for compatibility; the ready-order board remains the current operational dispatch path. Registration and proof files remain on their existing reviewed legacy Storage paths; this patch introduces no signed URLs or claims of private Rider documents.

## Verification

Focused tests use the real modules with an optimistic transaction harness, read-version contention, staged atomic commit failures and lost acknowledgements. They cover racing riders, two distinct Manager accounts crediting one request, concurrent claim/top-up wallet movements, exact prepaid receipt refusal, stale/revoked identities, approval decisions, decline history, ownership, original request preservation and actual Manager review wrappers. No live financial records or uploads are used.
